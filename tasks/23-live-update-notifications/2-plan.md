## Scope

Replace automatic adoption of other clients' task and note changes with an in-app notification asking whether to update. Keep SSE as a change detector, including reconnect recovery; removing live sync means removing automatic application, not removing the notification transport. Initial loading, genuine destination changes, and local-only file watching remain separate from this remote-update choice. Preserve the existing server/local reconciliation strategy only for first initialization and genuine destination changes, not settings dismissal or same-destination reconnection.

Do not modify implementation code during this planning stage. Implementation will affect the `app/` and `server/` Git submodules; record their commits and update the parent repository pointers during the implementation workflow. Do not touch `todo.md`.

## Implementation plan

### 1. Separate remote detection from applying content

- Replace the direct server-event-to-pane-refresh routing in `app/src/App.tsx`. Local watcher events should retain their current behavior; server events should request detection only.
- Add a small remote-update coordinator, with tests, under `app/src/lib/`. Make it the sole authority for accepted remote snapshots and approval state. Track pending and dismissed snapshots, per-resource read generations and local mutation epochs, and the active transport. Keep task and note state independent. Panes own rendering, drafts, and save provenance; any rendered snapshot is a projection, not a second independently advanced approval baseline.
- Define a narrow coordinator/pane contract: register initial applied content, begin/settle a local mutation, offer a remote snapshot, prepare an approved application, acknowledge application, and defer/review an offer. Use an immutable application token containing destination, transport generation, resource mutation epoch, and offered snapshot identity. Validate it immediately before pane application; acknowledge and advance accepted state in the same synchronous commit turn. Async preparation must not paint or advance the baseline, and canceled, failed, dirty-conflict, or IME-deferred application must not acknowledge success.
- Increment the resource mutation epoch at local mutation start and settlement, invalidating older detection and application tokens. Detection reads capture the epoch and read generation; discard stale results and schedule detection after outstanding writes settle. Retain incoming event evidence during writes rather than suppressing it. Successful writes advance only their known local content; failed or uncertain writes retain the previous accepted snapshot and pending evidence until a fresh read or explicit resolution establishes convergence. The coordinator observes mutation lifecycle without acquiring or duplicating the note pane's destination-specific save slots.
- Read changed resources without applying them to panes or writing backups. Compare canonical content with the accepted baseline, including empty notes and task deletions. Use an unfiltered task snapshot, not the current project view, and include task IDs in task identity comparisons because raw-file replacement can reassign them.
- Coalesce repeated signals into one pending update per resource. Repeated events for unchanged or declined content must not reopen the question automatically; a different remote version may prompt again. A current, epoch-valid read showing the accepted content clears its pending update. A local write completing is not sufficient evidence to clear a different pending remote snapshot.
- Replace `onConnected: refreshPanes` with detection of both resources after initial baseline establishment. Reconnect must detect missed changes without adopting them. Guard initial-load races so establishing a baseline cannot swallow a change received during loading.
- Preserve transport-generation checks, abort handling, subscription ownership, and bounded retries. Old reads, prompts, and choices must not affect a replacement connection. Failed detection keeps current content and shows a retryable error rather than implying that content is current.
- Separate destination identity from subscription/view generation in `App.tsx` and `api.ts`: use the server URL in server mode, and the local data-directory generation in local mode. Certificate changes and stream replacements invalidate old work but do not create a new destination. Run write-through startup reconciliation only on first initialization or a genuine destination change. Do not key it to unconditional `connectionKey` increments.
- Closing unchanged settings must neither activate a replacement destination nor run startup reconciliation or pane reloads. Apply UI-only settings independently. When the same destination needs transport reconfiguration, cancel old work, carry its accepted/pending/deferred state into the new generation, invalidate old application tokens, and detect content without adopting it. A genuine destination change initializes new approval state after the existing draft-safe handoff and reconciliation.

### 2. Identify self-originated changes

- Current server events carry only `tasks` or `note`; there is no author identity. Do not suppress all events during a local save or use a timeout, because this would also hide concurrent changes from other clients.
- Generate one random client-session ID in `app/src/api.ts`, separate from the per-subscription connection ID. Pass it through native HTTP mutations and the SSE handshake using an optional `X-Ntr-Client-Id` header. Extend `ServerRequest`, `server_connect`, and their tests in `app/src-tauri/src/http.rs` accordingly. Do not attach the ID to unrelated external requests or treat it as authentication.
- In `server/src/api.rs`, wrap broadcast changes with optional origin metadata. Successful task, raw-task, and note mutations attach the request's client ID. File-watcher changes have no origin. Preserve the existing `Change` resource enum and adapt internal sender/receiver tests as needed.
- Have `/api/events` omit events whose origin matches that subscriber's supplied client ID. Preserve the existing SSE event name and string payloads for all delivered events, and preserve delivery to clients without an ID. Other clients and out-of-band file changes must still notify normally.
- Replace silent `RecvError::Lagged` handling with an explicit rescan signal: emit both existing `tasks` and `note` tokens before resuming buffered changes, bypassing origin filtering for these two synthetic signals. Preserve the receiver and any queued second signal across stream polls. Updated clients perform side-effect-free detection for both resources; equal-content self-only overflow produces no prompt. Legacy clients still parse the same tokens but may automatically refresh both resources after lag; document this intentional recovery behavior.
- Successful local writes advance only their own accepted content in the client coordinator. Do not clear a different pending remote update merely because a local write completed.
- Document that precise self-event filtering requires the updated server. With an older server, retain the approval boundary and suppress equal-content echoes by snapshot comparison; do not claim reliable author attribution or discard differing updates as presumed self-events.

### 3. Add an explicit update choice

- Add `app/src/components/RemoteUpdateDialog.tsx` and matching tests/styles. Follow existing native `<dialog>` lifecycle, backdrop, and event-ownership helpers. Identify the changed resource and ask, for example, “Tasks changed elsewhere. Update now?” with `Update` and `Not now` actions.
- Queue task and note questions without stacking modal dialogs. Wait while settings, startup conflicts, or note conflict dialogs own the interaction; retain pending updates until they can be offered safely.
- `Not now`, Escape, and backdrop dismissal must be read-only: retain visible content and drafts, record the declined snapshot, and never write the local version to the server. Do not reuse the note conflict dialog's Keep mine handler for dismissal; it currently performs a PUT.
- Keep an accessible persistent pending-update indicator with a `Review update` action after dismissal, including on mobile. The action reopens the identical deferred snapshot without needing another event or restart. Revalidate through the normal detection path; offer changed content again and clear the indicator only on verified convergence or successful resolution. A failed revalidation retains the indicator and retry action.
- Model the per-resource lifecycle explicitly: `idle` receives a differing snapshot and becomes `offered`; dismissal becomes `deferred`; manual review becomes `offered` again; acceptance becomes `applying`; successful acknowledged application becomes `resolved`, then `idle`. Failed application returns to an actionable offer, and canceled or draft-blocked application remains unresolved. A different snapshot supersedes the offer with a new identity; a convergence read resolves it. Do not confuse “deferred” with “resolved.”
- `Update` authorizes only the identified resource and offered snapshot. If a refreshed read discovers different content, update the pending question rather than silently applying an unapproved replacement. Keep pending state on a failed read or application and offer retry.
- Expose asynchronous pane/coordinator outcomes so a click does not clear pending state before content is safely applied. Handle duplicate clicks and newer updates arriving while a choice is in progress.

### 4. Preserve note editing and save safety

- Extend `NotePaneHandle` and `app/src/components/NotePane.tsx` to distinguish initial/recovery reads, remote detection, and an explicitly accepted remote snapshot. Register initial applied content and successful local save results with the coordinator. Keep `savedNote`, edit revisions, and save provenance private as persistence-safety evidence; they must not independently grant remote approval. Apply an approved snapshot only with a current coordinator token and acknowledge it through the shared contract, without exposing editor DOM ownership.
- On remote detection, preserve the current editor text, selection, history, and saved baseline. Suspend pending autosave, blur, pagehide, and follow-up saves while a differing remote note awaits a decision, so opening the prompt cannot overwrite the incoming version.
- Accepting an update for a clean note adopts the offered snapshot through the existing editor-write path and preserves sensible caret offsets. A dirty note still requires the existing explicit unsaved-edit choice before replacement; accepting the notification alone must not discard a draft.
- Declining leaves the note and server untouched. Retain a remote-divergence save guard while that snapshot remains unresolved; a later local save must obtain an explicit keep-local/overwrite choice rather than silently replacing the declined remote version. Escape from the notification must never authorize that overwrite.
- Display a clear “Remote update pending; automatic saving paused” status with `Review update` while a declined note remains divergent. Debounced autosave, blur, and pagehide stay blocked without repeatedly reopening dialogs. The user can review at any time, including before editing a clean note. Review first offers the remote update; if a dirty draft remains, hand off to the existing explicit version-choice flow. Only explicit Keep mine authorizes an overwrite. New input must retain the draft and visible review action, not silently resume saving.
- Preserve single-flight save ownership, transport scoping, baseline-return draft protection, empty-text handling, and deferred reconciliation during IME composition or a PUT. An already issued PUT cannot be recalled; after settlement, recheck pending evidence without automatically adopting new remote text.
- Audit internal recovery paths and `ResourceRefresh` callbacks so reconnect, retry, or stale-save recovery cannot bypass the approval gate for a differing remote snapshot. Necessary reads may continue; applying remote content requires the relevant choice.

### 5. Keep task refreshes behind the same approval boundary

- Update `app/src/components/TodoPane.tsx` to render the coordinator's accepted unfiltered task snapshot and derive project filtering/sorting locally. Any pane-local copy is a read-only projection of acknowledged content. A project-filter change must not fetch and display a declined remote version.
- Apply accepted remote snapshots explicitly, including the associated label reads, without clearing add/edit drafts or unexpectedly closing task dialogs. Queue application while a task edit needs protection, or request a separate explicit discard choice.
- Replace unconditional post-mutation full-list refreshes with updates from successful mutation responses or targeted removals against the accepted snapshot. Apply server-returned timestamps and IDs for the user's own actions without importing unrelated remote changes. Refresh remembered labels deliberately rather than using label loading as a hidden full-task refresh.
- Audit error refreshes, project removal, edit completion, and settings callbacks for accidental remote adoption. Explicitly changing the connection may load its initial content; merely closing unchanged settings must not accept a declined update.
- When pending task changes make the visible task IDs unsafe, require an update before edit, complete, delete, or bulk project removal, preserving drafts. Do not send stale-ID mutations or silently update the view as a side effect of clicking an action. Last-write-wins races after a validated action remain an existing storage limitation.
- A blocked task action must expose `Review update` even when the relevant snapshot was previously declined. Route it through the same actionable offer rather than leaving the button inert. Preserve edit/add drafts during review and never replay a stale-ID mutation automatically after updating; the user must choose the action against the updated task identity.

## Acceptance criteria

- Another client's task or note change produces an in-app update question without automatically changing displayed content.
- `Update` loads only approved content and preserves existing unsaved-edit protection. Newer content requires a new choice.
- `Not now`, Escape, and backdrop dismissal keep displayed content and drafts unchanged and perform no server writes. Repeated identical notifications do not automatically reopen the question, but `Review update` can reopen and accept the same version without another event or restart.
- Local changes do not trigger remote-change questions with the updated server, including SSE events arriving before mutation responses. Concurrent foreign changes remain detectable.
- Reconnection detects missed changes but does not apply them. Initial loading and local-only file watching remain functional.
- Filter changes, local mutation refreshes, retries, and unchanged settings cannot silently import declined content. Unsafe stale task actions request an update first.
- Unchanged settings and same-destination transport reconfiguration retain approval state and do not run startup reconciliation under any conflict strategy. Only first initialization and genuine destination changes invoke that write-through flow.
- The coordinator alone commits accepted snapshots. Detection reads and application tokens invalidated by local mutations cannot roll back content or produce self-change prompts; concurrent foreign changes remain pending until verified convergence or explicit resolution.
- Broadcast overflow triggers detection of both resources even if all retained events are filtered self-events. A lost foreign update becomes reviewable without another mutation or reconnect, and neither pane changes until approval.
- Pending remote notes cannot be overwritten by automatic saves while awaiting a safe, explicit decision. Existing draft, IME, empty-note, transport, and single-flight protections remain covered.
- Deferred notes show paused-save status and an actionable review control. Blocked stale-task actions lead back to review while preserving drafts and never automatically replaying old task IDs.
- Relevant automated checks pass; implementation records verification limits and documents the changed behavior and server compatibility.

## Risks and decisions

- Use in-app prompts, not operating-system notifications; no new notification permission or platform plugin is needed.
- Declining means “do not load this remote version now,” not “push mine” or “never offer review again.” Existing Keep mine conflict resolution is a separate explicit overwrite action. Persistent review controls are required because unresolved remote notes pause automatic saving and unsafe task identities block mutation.
- Origin filtering requires an additive server/native change because current resource-only events cannot reliably distinguish authors. Older clients retain their existing wire format and behavior; updated client plus updated server is the supported pairing for precise self-event suppression.
- Content detection reads must remain side-effect-free. Existing backup and startup reconciliation code is not an appropriate remote-detection primitive.
- The server remains last-write-wins; this task does not introduce collaborative merging, persistent revision history, or transactional compare-and-swap writes. A write already in flight may race another client, and a disconnected client cannot detect changes until connectivity returns.
- Startup server/local conflict strategy stays unchanged only at first initialization and genuine destination changes. Runtime remote-update approval, unchanged settings, and same-destination transport reconfiguration must not inherit automatic server/local reconciliation strategies. Destination identity is separate from transport generation and certificate policy.
- The coordinator owns accepted approval snapshots; panes retain only rendering projections and private draft/save evidence. Resource mutation epochs prevent pre-write reads from being misclassified after local writes, without introducing server-side revisions or a second note save-lock implementation.
- Lag rescans deliberately bypass origin filtering but do not bypass client snapshot comparison or approval. Legacy clients may refresh both resources automatically on lag; existing wire tokens and parsing remain compatible.
