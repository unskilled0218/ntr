## scope

Fix package association for the deployed service reporting `28.2.0`, add clear progress logs, and provide explicit verified recovery for the accepted `v0.2.6` publication without rebuilding or republishing it. Preserve the supported Gitea `1.25.x` path, conflict/hidden-link protections, exact publication identity, bounded evidence, and no-blind-retry policy. Changes are confined to `server/` release tooling, tests, metadata, documentation, and the parent pointer/task report. No application changes, ARM64 v8/F2 fix, real-token access during verification, live publication/link mutation, cleanup, privileged setup, or edits to `todo.md` are authorized.

## Implementation Plan

### 1. Establish and document the supported server contract

- Planning used unauthenticated read-only HTTPS GETs, without credentials. `https://git.lan/api/v1/version` reports `{"version":"28.2.0"}`, the homepage identifies Gitea, and `/api/v1/settings/api` returns Gitea-style settings. Upstream `go-gitea/gitea` has official tag `v28.2.0`: annotated tag object `1dc1ecdddcdc60ab14ec14e30e7bb4d84242f21f`, peeled commit `829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1`. This establishes a matching published Gitea version/contract, not cryptographic attestation of the installed binary. If implementation discovers a custom/forked deployment, require operator build provenance and refuse new writes until its behavior is reviewed.
- Pin further contract inspection and documentation to that exact upstream commit, not moving `main`: `routers/api/v1/packages/package.go`, `services/packages/package_update.go`, `services/convert/package.go`, `models/packages/package.go`, and the relevant API route/middleware and tests. Compare the supported `v1.25.0` implementation. Record exact source links and relevant permission/conflict/status semantics in a dedicated `server/docs/package-association-contract.md`.
- Inspected `LinkToRepository` rejects owner mismatch, rejects any positive existing `RepoID` before writing, checks package-unit write permission, then sets the link. The API maps invalid-argument conflict to HTTP 400, permission denial to 403, and success to an empty 201. The serializer can hide inaccessible repository links as null. The model update is not compare-and-set; preserve exclusive package/association writers as an operator prerequisite and do not claim distributed atomicity.
- Planning also read public release/tag endpoints for `v0.2.6`. Reported tag object: `48ef6113e6fb296554193c11a147abcdb0aa002e`; source: `7bc9b8c344f4654f90f494e1fe7966d13526bfb5`; bound index: `sha256:0c61b7b7019da16b683c772ecc68118c58837fe356b1f9119ab0f762e32dc925`. These are observations to reverify, not trusted constants authorizing a write. The unauthenticated package GET returned 401, so neither current association nor registry identity/account authority has been established. Do not read a real token to fill that gap during implementation verification.

### 2. Extend association support without weakening refusal

- During implementation create fresh parent/server branches named `20-package-association-compatibility-logs`. Keep this planning stage documentation-only.
- Replace the inline version regex in `package_association` with a small named contract classifier in `scripts/release-data.py`. Preserve stable Gitea `1.25.x` recognition and add only exact stable Gitea `28.2.0`, justified by the pinned review. Do not allow every `28.x`, arbitrary newer versions, development/prerelease/build-suffixed versions, guessed Forgejo compatibility, or an operator bypass switch. Keep family/provenance assumptions explicit in documentation; a version string alone cannot attest a modified server.
- Keep correct existing links read-only without requiring the new-link version gate. For null links, require exact target/package identities, explicit nullable repository evidence, literal package version `latest`, positive IDs, and refreshed evidence before at most one scoped bodyless link POST. Visible conflicts refuse; hidden existing links must be refused by the reviewed server service rather than reassigned.
- Preserve empty-201 validation, fatal unexpected HTTP/input/size failures, one read-based reconciliation after lost transport response, exact readback, and final publication/link verification. Never unlink, retry a blind POST, force a link, roll back accepted state, skip required association, or mark incomplete publication as successful.

### 3. Add identity-bound existing-publication recovery

- Do not solve recovery by changing the current no-argument publisher to accept mismatched script/config hashes. `inspect_tag` deliberately binds those hashes to the publishing checkout; updating code and preparing `0.2.7` means a normal invocation cannot safely impersonate the old `v0.2.6` transaction.
- Add an explicit mode to the existing Bash entry point: `--associate-existing <tag> --expected-tag-oid <40-hex-object> --expected-source <40-hex-commit>`. Require all arguments, validate strict syntax and reject duplicates/extras before credentials, locks, temporary state, or commands. Retain existing no-argument publication, offline `--validate`, and Bash-only `--help`; update the lock wrapper to forward the validated mode/arguments rather than silently dropping them. Do not introduce a generic resume/repair mode.
- Require a clean current server `main`, exact configured fetch/push destinations, and current source/config/scripts stability throughout recovery. Preserve the publisher's clean/already-pushed-main policy for the updated recovery tool as well; source pushes remain a separate approved operator action. Require the explicitly expected historical source to be an ancestor of current verified `main`. Current configured origin/repository/image must agree with the old publication; tokens/login come from current protected external credentials, not historical secrets.
- Obtain fresh complete remote tag/release inventories for the requested historical tag, require the supplied exact tag OID and peeled source, fetch only that expected object without moving local tags, and require the local historical source to be available. Read historical settings, `VERSION`, Cargo/README mirrors, notes, and all three release scripts as bounded regular committed Git blobs from the explicitly expected source. Never execute, source, or import historical scripts, and do not check out/rewrite the live tree to read them.
- Factor historical data validation/identity construction so the same canonical rules remain enforced. Recompute the old raw settings hash, ordered script hash, normalized committed notes digest, and deterministic annotated-tag bytes; verify the fetched object's exact bytes/OID and all `container-release-bash/1` fields against those historical inputs and current target scope. Historical metadata must be parsed against an explicitly supported schema; unknown format, symlink/missing/oversized blobs, invalid paths, foreign identity, supplied pin mismatch, or altered notes/config/scripts refuse before any POST. Keep the ordinary publisher's current-checkout identity check unchanged.
- Verify the historical release body/state and immutable index's AMD64/ARM64 manifests/config labels against the historical version/source. Require current `latest` to equal that exact bound digest; a missing/advanced/foreign alias refuses without promotion. Preserve conservative inventory refusal of ambiguous/newer publication states rather than granting authority to repair them.
- Recovery uses Git/curl/Python and API/registry read credentials only: split credential preparation from Docker/plugin isolation as needed without weakening normal publishing. Do not require or invoke Docker/Buildx inspection, bootstrap, login, snapshot/build, tag push, alias promotion, release POST, archive upload, or any remote mutation other than the single permitted package-link POST. Read-only Git fetching may populate local objects; it may not replace local refs or execute remote-provided code.
- Reverify both current tool identity and historical publication evidence immediately before association and after accepted association, using shared association logic and equivalent final guards rather than weakening `publication_guard`. Correct existing links require no write. A successful repeat is read-only. Failed evidence returns nonzero and preserves accepted objects; no rollback or cleanup follows.

### 4. Add visible secret-safe progress

- Introduce a small stderr progress helper in the existing release scripts/helper. Print prompt phase transitions with elapsed time for local validation, source/builder checks, startup classification, staging reuse/build, immutable verification, tag push/readback, digest promotion, release creation, existing-publication verification, association contract checks, link/already-linked outcomes, and final verification. Keep existing success references on stdout; logging must not corrupt JSON, digest, HTTP-status, or field output consumed by command substitution.
- Emit truthful state-specific messages: distinguish publication verified but association incomplete, mutation attempted but outcome uncertain, accepted response reconciled by readback, completed read-only retry, and fully verified success. Do not report a write as confirmed before evidence establishes it. Refusals must identify the phase and preserve the original nonzero status.
- For long-running bounded subprocesses, especially the two-hour build, emit a rate-limited fixed-text heartbeat, for example every ten seconds, while draining pipes concurrently. Use monotonic elapsed time, retain deadlines/byte caps/process-group cleanup, and stop heartbeat output after completion/failure/signals. Avoid a background heartbeat that outlives the owned operation; do not write per-iteration or unbounded logs.
- Use fixed or validated non-secret labels, never raw command arguments, environment dumps, token paths/content, private auth config, authorization headers, API bodies, or subprocess stdout/stderr. Do not restore raw build-log streaming or enable shell tracing. Generic progress plus elapsed time satisfies visibility without creating a new secret-redaction dependency. Help/validation remain credential-free and effect-free apart from their intended terminal output.

## Acceptance Criteria

- Exact supported stable Gitea `28.2.0` can authorize a missing association under the reviewed contract without broadening to unreviewed versions or weakening supported `1.25.x` behavior. Unknown/conflicting/hidden-link evidence cannot authorize reassignment, repeated POSTs, or false success.
- Explicit recovery verifies supplied tag/source pins and historical source/config/scripts/notes/image identities independently of updated current tool version. It can complete the accepted `v0.2.6` association without Docker, rebuild, tag/release/image writes, latest promotion, or any rollback. An existing correct link and repeat invocation are read-only; changed/foreign/partial evidence refuses safely.
- Normal publication remains strict about current source/config/script identity, selected builder/auth isolation, exact non-force no-follow-tags publication, and final association. Historical recovery is not a general bypass or arbitrary code execution mechanism.
- Users see prompt phase messages and bounded heartbeats during long waits, with clear incomplete/uncertain/verified outcomes. stdout data contracts and nonzero statuses remain intact; credentials, arbitrary tool output, and sensitive API data are never relayed.
- New tests reach their intended faults and assert observable state preservation and prohibited writes, not just nonzero exit. Relevant verification passes or exact environment blockers are recorded. Metadata/docs agree on prepared `0.2.7` while preserving the historical `v0.2.6` publication.
- No live publication/recovery/link mutation, production credential access for tests, cleanup, host administration, dependency upgrade, F2 fix, application change, or `todo.md` edit occurs during implementation.

## Risks And Decisions

- Official Gitea `28.2.0` is a real upstream release; it must not be guessed to be Forgejo from its version number. Self-reported API/version branding and upstream contract review are not installed-binary attestation. Custom builds require explicit provenance review, not an allow-all version regex or a guessed compatibility switch.
- Hidden associations remain possible because serialization is permission-filtered. The reviewed service's already-linked refusal plus exclusive writers is essential; client null checks alone cannot prove unlinked state. The server model update is not atomic compare-and-set, so concurrent UI/API writers and in-flight operations remain disallowed.
- The accepted annotation binds the old script hash. A version/regex/logging-only patch cannot by itself recover the old release through the ordinary entry point. Explicit pinned historical verification separates authority from the new executable and avoids rewriting evidence to manufacture ownership.
- Recovery should share pure parsing/verification and association policy, not fork the publisher or execute an old checkout. Its larger verification surface is justified by the explicitly requested safe completion; avoid adding generic journals, arbitrary hooks, cleanup tools, or silent adoption.
- More logs can leak credentials or falsely imply completion. Fixed messages, stderr separation, rate-limited monotonic heartbeats, bounded capture, and exact evidence-based outcomes are required. Raw subprocess streaming is deliberately out of scope.
- The real package endpoint was inaccessible without authentication during planning. Existing publication observations are not proof of present registry state or token rights. Missing permission/provenance/current evidence may remain an operational blocker; do not weaken checks or perform a live mutation to resolve uncertainty during tests.
