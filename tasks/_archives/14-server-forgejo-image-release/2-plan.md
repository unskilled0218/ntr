# plan

## scope

Implement a versioned server container build and Forgejo registry publisher for both `linux/amd64` and `linux/arm64` in the `server/` submodule, and switch `server/docker-compose.yml` to that published multi-platform image. Add `server/Dockerfile`, `server/.dockerignore`, `server/scripts/release.sh`, focused script tests, and dedicated release documentation. Update the existing Compose documentation and its brief README navigation. Preserve Rust application behavior, API contracts, and file formats.

The server is currently `my-ntr-server` version `0.2.1`. Compose mounts source into `rust:1-bookworm` and runs `cargo run --release`; it has no packaged server image. Its published port is actually `0.0.0.0:8080:8080`, despite comments describing configurable loopback binding, and its health URL contains an extra `}`. Address those deployment inconsistencies while replacing the source-build service.

## Implementation Plan

### 1. Define the release identity and configuration

- Create fresh `14-server-forgejo-image-release` implementation branches in the parent and server repositories when implementation begins. Keep app revisions unchanged.
- Default the registry to `git.lan` and image repository to `git.lan/ntr/ntr-server`, following the existing Forgejo host, owner, and server repository name. Forgejo container names use `{registry}/{owner}/{image}` and publish to Packages, not release attachments. Allow `FORGEJO_REGISTRY` and `FORGEJO_IMAGE` overrides, validate their consistency, and reject image repositories containing a supplied tag or digest.
- Read the version through `cargo metadata --no-deps --format-version 1`, selecting the `my-ntr-server` package with Python's standard JSON parser rather than grepping Cargo.toml. Use the current crate version as the image tag, initially `0.2.1`; do not add `latest`, change the crate version, create Git tags/releases, or push source as part of this publisher.
- Require a clean server `main` checkout for release publication and capture its full Git revision. Add OCI version, revision, and source labels; source defaults to `https://git.lan/ntr/ntr-server`. Publish one version tag pointing to an OCI image index containing both `linux/amd64` and `linux/arm64`; use identical version/revision labels for both platform images.
- Require `FORGEJO_TOKEN`. Accept `FORGEJO_USERNAME` as the token owner's login name, independent of the package owner `ntr`. To support the exact token-only command in the goal, resolve the login using authenticated `GET https://<registry>/api/v1/user` when the username is absent. Parse `login`, validate HTTP/JSON responses, and explain that this mode needs `read:user`; explicit username mode avoids that lookup. Allow a separate `FORGEJO_API_URL` base override for deployments with different API routing.
- Document package-write permission and permission to publish under `ntr`, rather than reusing the app publisher's repository-write-only token instructions. Keep TLS verification enabled and use the engine's existing registry trust configuration.

### 2. Build a standalone server image

- Add a multi-stage Dockerfile with a compatible Rust Bookworm builder and Debian Bookworm slim runtime, verifying both base images support amd64 and arm64. Let each stage use Buildx's target platform rather than pinning the Rust builder to `$BUILDPLATFORM`, so Cargo builds the correct target binary natively or under configured emulation. Build `my-ntr-server` using `cargo build --release --locked --bin my-ntr-server` and copy only the resulting binary into the matching runtime stage. Install required runtime libraries, CA certificates, and curl in the image build, not in this workspace or host environment.
- Set an exec-form entry point for the server, working directory `/data`, and image defaults `HOST=0.0.0.0`, `PORT=8080`, `TODO_FILE=/data/todo.txt`, `NOTE_FILE=/data/Note.md`, and `LABELS_FILE=/data/labels.json`. Preserve all existing environment overrides, including `TODO_ADD_CREATION_DATE`.
- Provide a writable `/data` directory owned by a non-root runtime user with a documented numeric UID/GID. Document that bind-mounted data must be writable by that runtime identity and allow a runtime user override. Do not automatically change ownership of users' existing data.
- Add OCI build arguments for version, revision, and source. Make curl available for the Compose health check, and verify runtime linkage against the selected base image.
- Add `.dockerignore` exclusions for `target/`, `.git`, runtime data, root task/note/label files, credential files, and generated release output. Retain Cargo manifests, Cargo.lock, source, and any files needed for the build. Verify runtime data and secrets cannot enter image layers through the build context.

### 3. Implement the release script

- Add executable `server/scripts/release.sh` using Bash strict mode. Resolve the server root from `BASH_SOURCE`, so both `server/scripts/release.sh` from the parent and `scripts/release.sh` from the server work independently of the current directory.
- Preflight Bash, Git, Cargo, Python 3, curl, Docker, the Buildx plugin, and daemon access with actionable errors. Resolve `BUILDX_BUILDER` or the currently selected builder to one explicit name and pin that name for subsequent inspection/build commands. Support an existing `docker-container` driver builder as the initial baseline; reject the classic default `docker` driver and other unverified drivers with setup instructions. Validate credentials, image configuration, branch/clean state, and package version before publishing.
- Use a private temporary directory and isolated `DOCKER_CONFIG` for registry login and Buildx publication, with an exit trap that removes temporary credentials. Before switching configuration, resolve the original Docker configuration path, Buildx state path, effective engine/context, and named contexts used by every selected builder node. Keep `BUILDX_CONFIG` explicitly bound to the original Buildx state path, preserving an existing override, so changing `DOCKER_CONFIG` does not select a different builder. Export/import only the required named Docker contexts into the temporary configuration, retaining their connection/TLS settings and any explicit `DOCKER_HOST`/TLS environment overrides; preserve plugin discovery through the original plugin directory. Do not copy unrelated registry authentication, change the user's current context/builder selection, or remove the user's builder during cleanup.
- After configuration isolation, verify the Buildx plugin remains discoverable, engine connections work, and `docker buildx inspect --bootstrap` for the pinned builder still reports the expected `docker-container` driver and both `linux/amd64` and `linux/arm64`. Check the driver as well as the platform list: advertised execution platforms alone do not prove multi-platform export support. Pass the token through `docker login --password-stdin`; do not put it in command arguments, trace output, or repository files. Send API authorization through curl configuration on stdin rather than a token-bearing command-line header.
- Run `cargo test --locked` before building or publishing. Build from the server Dockerfile/context with the computed image tag and OCI labels using `docker buildx build --platform linux/amd64,linux/arm64 --push`, the pinned builder, and `--metadata-file` in the private temporary directory. Parse and require a valid `containerimage.digest` from build metadata. Do not use `--load`, which does not reliably load a multi-platform index into the classic local image store. A failed test prevents the build/push; a failed platform build must not be reported as a complete release even if intermediate registry blobs were uploaded.
- Define one registry-inspection helper returning missing, valid, or error, plus a validated index digest and platform/digest map when valid. Use `docker buildx imagetools inspect --format '{{json .Manifest}}'` to resolve a reference and parse it with Python; require a supported OCI index or Docker manifest-list media type and a valid SHA-256 digest. Pin all subsequent index inspection to `image@<index-digest>`. Require exactly one runnable descriptor for each target architecture, accepting `linux/arm64` with absent variant or variant `v8`; ignore descriptors explicitly marked as attestation manifests and reject malformed, duplicate, unsupported runnable-platform, or incomplete responses. For each selected child digest, fetch `--format '{{json .Image}}'` at `image@<child-digest>` and validate configuration OS/architecture and OCI version/revision labels, rather than looking for labels on the index or relying on host-platform selection. Use this same helper for existing-tag decisions, reruns, and post-push checks.
- Authenticate and inspect the existing version tag before starting the build/push. A missing reference must match a narrowly defined, supported Buildx missing-manifest diagnostic for the requested repository/tag; test it against a known absent tag in the authenticated target namespace during live verification and document the tested Buildx version. Do not equate all nonzero exits or arbitrary `not found` substrings with absence. Authentication, transport, permission, malformed-output, and unrecognized diagnostics are errors that prevent publication. Reuse an existing index only when both required platform configurations match the expected version/revision, reporting its index and platform digests; reject conflicting revisions or incomplete platform sets.
- Publish a new version only after successful preflight and conflict checks. Inspect and validate the immutable index identified by the build metadata digest, then resolve the version tag again and require that it points to that same digest before reporting success. Report the image reference, index digest, per-platform digests, version, and revision. A failed or ambiguous push, missing/malformed metadata, index verification failure, or moved tag returns nonzero; rerunning inspects remote state before retrying and does not delete published packages.
- Keep the script linear with small helpers for configuration, login-name resolution, and remote image inspection. Do not add Forgejo release-attachment operations or CI infrastructure.

### 4. Switch Compose to the Forgejo image

- Set the service image to `${NTR_IMAGE:-git.lan/ntr/ntr-server:0.2.1}`. A full-reference override supports another registry, another version, or `image@sha256:<digest>` without maintaining a second version field.
- Leave the Compose service platform unset so Docker selects amd64 or arm64 from the same published index based on the deployment host. Digest-pinned examples should use the index digest when retaining automatic platform selection.
- Remove the Rust source-build command, source working directory/mount, Cargo cache mounts, and their top-level named volumes. Keep `./data:/data`, the existing runtime environment, and `restart: unless-stopped`.
- Set host port mapping to `${NTR_BIND:-127.0.0.1}:${NTR_PORT:-8080}:8080`, restoring the behavior the documentation promises. Keep `HOST=0.0.0.0` inside the container so published ports work; distinguish container binding from host exposure.
- Correct the health check to `curl -fsS http://127.0.0.1:8080/api/health`, using the packaged curl executable. Reduce the source-compilation startup grace period to a measured allowance for binary startup; retain reasonable intervals, timeouts, and retries.
- Validate bind-mount permissions without changing user files. Document a compatible `user` override when needed and confirm that atomic sibling-temp writes and rename work for all three mounted resources.

## Acceptance Criteria

- The requested token-only command works through documented login-name resolution and publishes `git.lan/ntr/ntr-server:0.2.1` by default, or the configured image, with the intended revision and reported registry digest.
- The published version tag references one image index containing runnable `linux/amd64` and `linux/arm64` images with matching version/revision labels. Report the index digest and both platform digests, and verify startup/persistence on each platform or explicitly record unavailable runtime checks.
- The runtime image contains the compiled server and starts without compiling or mounting source. Runtime environment overrides and mounted task/note/label data retain existing behavior.
- Compose pulls the Forgejo image, has configurable loopback-default host exposure, a valid working health check, and persistent data across image replacement.
- Release failures stop publication and return nonzero. Existing version tags from another revision are not silently overwritten; same-revision reruns report the existing published digest.
- Credential isolation preserves the explicitly selected supported builder and engine contexts. Platform support is checked after isolation, and no original registry credentials, global builder selection, or Docker context selection are changed.
- Existing-tag and post-push validation use one machine-readable, digest-pinned inspection contract. Success requires valid configurations for both runnable platforms and agreement between the build metadata index digest and the version tag; ambiguous lookup failures never authorize a push.
- Focused script tests and Rust checks pass. Actual image build/runtime/persistence and live publication checks pass when the required engine/registry are available, with any missing verification explicitly recorded.
- Dedicated documentation covers publishing, login permissions, Compose startup, image/version overrides, data permissions, and upgrades. README remains concise.

## Risks And Decisions

- The default image repository is confirmed from the existing Git origin and Forgejo's naming rules. The account username cannot be inferred from Git author metadata; resolve it from the supplied token or explicit `FORGEJO_USERNAME`.
- Forgejo package publishing requires package permissions. A token previously used for app repository releases may lack `write:package` or the optional username lookup's `read:user`; documentation and errors must distinguish these cases.
- Registry inspection can fail for reasons other than a missing tag. A rerun must not convert access or network errors into an overwrite. Version labels and Git revision establish source identity; `--locked` does not promise byte-identical images across changing base-image digests.
- Buildx's default state path depends on `DOCKER_CONFIG`; isolate registry credentials while explicitly retaining the original Buildx state and the selected builder's required connection contexts. The initial driver support is `docker-container`, so broad platform advertisements from an unsupported driver are not enough to proceed.
- Image index descriptors do not carry the Dockerfile's OCI labels. Validate each selected child image configuration by digest and compare the final index with build metadata; human-readable CLI summaries are not the release identity contract. Buildx error diagnostics vary by version, so untested or ambiguous missing-reference responses fail closed.
- Docker registries do not provide a universal compare-and-swap for tags. The script's conflict check protects normal serial releases; concurrent publishers for the same version remain unsupported and must be documented.
- Preserve server version `0.2.1` for its first image. Later conflicting releases require a deliberate Cargo version update and matching Compose default; no automatic version bump or mutable `latest` alias is introduced.
- Both amd64 and arm64 are required release targets. Use native Buildx nodes or preconfigured emulation; availability of one host architecture does not prove the other image builds or runs. An incomplete index is not a successful release, and missing builder/emulation support must be reported rather than silently falling back to a host-only image.
- Image directory ownership does not override host bind-mount permissions. Verify atomic writes with the documented runtime user before deployment, and never change existing data ownership automatically.
- The current Compose file exposes all interfaces while its documentation claims loopback defaults. The planned loopback-default mapping follows the documented contract; users needing remote access must set `NTR_BIND=0.0.0.0` explicitly.
- Live publication follows committed server-main code because the script rejects dirty and feature-branch releases. Fixture tests and locally labeled image smoke tests provide pre-merge verification; missing Docker/registry access is a recorded limit, not evidence of success.
- This planning stage changes only `2-plan.md` and commits that document. Implementation and publication occur later.
