## scope

Implement task 28 in the `app/` submodule. When a configured server cannot be reached, automatically display the existing local tasks, note, and label suggestions instead of leaving the app showing only `Could not load label suggestions: error sending request for url (server-url)`. Reuse the existing local Tauri commands and local editing behavior. Preserve the configured server URL and provide an explicit reconnect path. No server changes, new synchronization queue, or implementation changes during this planning task.

## Implementation Plan

### Summary

`app/src/api.ts` currently derives every transport context directly from `getServerUrl()`. Its read functions never fall back to local commands. Startup reconciliation catches network errors and returns an empty conflict list, so `App.tsx` mounts panes that still read from the unavailable server. `TodoPane.tsx` reports task and label read failures, while the native SSE bridge retries separately. Fix the shared transport destination rather than hiding errors or independently substituting local results in each pane.

### 1. Distinguish connection failures

- Update `app/src-tauri/src/http.rs` to expose a structured, serializable connection-failure category for resource requests, retaining the original human-readable message. Categorize connection establishment, DNS, TLS, and GET timeout failures without parsing error strings. Keep HTTP responses as responses, including non-2xx statuses; keep malformed URLs, invalid methods, and internal IPC/client errors distinct from server unavailability.
- Normalize these failures at the `serverFetch` boundary in `app/src/api.ts`. Preserve the existing `<status> <statusText>` HTTP error contract and teach `errMsg` to retain native structured messages.
- Trigger automatic fallback only for a current server resource GET with a recognized connection failure. Do not use SSE failure alone as evidence that resource requests cannot work. Do not redirect or replay a failed mutation locally, since its server-side outcome may be unknown.
- Retain the existing 30-second GET deadline. Test timeout classification with short injected deadlines rather than waiting 30 seconds.

### 2. Own fallback in the transport

- Add session-only effective connection state in `app/src/api.ts`, separating the saved configured URL from the active server or local destination. Extend immutable transport context validation to cover both settings identity and effective mode; keep local data-directory generation in local destination identity.
- Add a transport-state subscription for `App.tsx` and a single idempotent transition into local fallback. The first qualifying failure must increment the transport generation synchronously, invalidate the failing server context, and notify subscribers; simultaneous failures must not produce repeated activations.
- Represent transition readiness separately from effective destination: each generation starts initializing with note and task/label mutation readiness closed. Close these gates synchronously with invalidation, before notifying React. Open each resource only after storage ordering, reconciliation, its current-generation projection, and any required destination/draft choices are complete. Read failures keep the affected gate closed with a visible error; another resource may become usable independently.
- Have `captureTransport`, `isTransportCurrent`, `destination`, resource reads, mutations, backup guards, and `onChange` use the same effective destination. Once local fallback is ready, task IDs and all newly admitted user writes must belong to the local store, not the configured server. Already-issued server mutations retain their original ownership and are never replayed.
- Guard all user mutation entry points in `api.ts`, including create, complete, delete, note persistence, and label/project writes, against resource readiness as well as context validity. Reject rather than queue or replay actions during initialization. Do not let a newly captured context authorize a form or task projection that belongs to the previous destination. Keep a narrow internal path for generation-checked reconciliation writes; it must not make public user mutations ready.
- Do not transparently retry the failing GET with local results under its old server context. Let the old request become obsolete and let the app reload all resources under a fresh local context.
- Ensure startup `reconcileWithServer` stops after invalidation and cannot return stale conflicts or continue copying resources after fallback. Let local initialization finish even if reconciliation failed before panes mounted. A stale failure from an old URL, certificate policy, or data directory must not activate fallback for the new destination.
- Give transport initialization a normal session lifecycle that also initializes effective mode and readiness in isolated tests. Do not rely on clearing localStorage to reset module-level fallback state, or add test-only production reset methods.

### 3. Apply destination changes safely

- Refactor the destination-transition handling in `app/src/App.tsx` so settings changes, fallback, and explicit reconnect share one lifecycle. Update `activeContext`, activate `RemoteUpdates`, invalidate conflict offers, rebind subscriptions, and initialize or refresh panes once for the new destination.
- Keep panes mounted and drafts visible while initialization is pending, but disable submit, completion, deletion, project actions, and destination-bound persistence until their resources are ready. Pause note debounce, blur, and pagehide writes immediately. Do not reuse the initial `ready` rendering flag to unmount already-mounted panes. Retained create/edit forms must establish their new destination explicitly before submission; stale task actions require a new action against the loaded identity. Apply these rules in both fallback and reconnect directions.
- Reuse `NotePane.prepareDestination` and its destination-aware save ownership to retain dirty text without automatically copying a server draft into local storage. Keep the existing explicit version-choice flow when a retained draft differs from the new destination. Do not remount panes to implement fallback, since that would lose drafts and pending save ownership.
- Refresh tasks and remembered labels together under the local context, clear obsolete server read errors, and prevent actions on an old task projection before local tasks are loaded. Audit `TodoPane.tsx` edit ownership, project rename/removal records, queued callbacks, and mutation validation so old server IDs cannot operate on coincidentally matching local IDs. Retain drafts without automatically replaying actions.
- Stop obsolete server subscriptions and resource retries; enable local file watcher refreshes. Cancel old remote approval tokens and ensure local reads are not registered as accepted server snapshots in `app/src/lib/remoteUpdates.ts`.
- Guard late server reads, reconciliation results, backup dispatches, and pending mutation continuations with their original context. An already-issued server request may settle, but cannot paint over current content, dispatch a new obsolete backup, or release another destination's note-save ownership. Completion guards cannot cancel an already-dispatched native file write; order those writes explicitly as follows.
- Centralize admission and tracking of native local writes in the transport facade. Register each operation synchronously before invoking Tauri, with its originating context and target storage generation. Include server backups of notes/tasks/labels, reconciliation writes into local files, and ordinary local writes that may still be pending when reconnect starts. Reject obsolete admissions; register no continuation after its generation is invalidated. This is an in-flight ordering barrier, not an offline synchronization queue.
- On fallback, invalidate server admission immediately, then drain already-admitted local writes before reading the local projection or enabling local edits. On explicit reconnect, drain prior admitted local writes before reading reconciliation baselines or applying new reconciliation writes. Use the same ordering boundary before data-directory changes. Do not drain unrelated pending server PUTs; late server results must fail the original context check before any backup admission. An old native backup may finish before local initialization, but must never overwrite an edit enabled afterward.
- If an admitted native local write rejects, wait for settlement, surface its error, reread actual storage, and do not report that it committed successfully. If it never settles, retain mounted content/drafts with `Waiting for local storage` status and keep affected initialization and mutation gates closed. A timer may expose that status, but must not falsely unlock writes or pretend the native operation was canceled. Preserve settings access without allowing a data-directory transition to bypass the barrier.

### 4. Show fallback and support reconnect

- Update `app/src/components/SettingsButton.tsx` and connection details in `SettingsModal.tsx` to reflect the effective local mode while preserving the saved server URL in the input. Add a small accessible status such as `Server unavailable; using local files` rather than presenting the raw label error as the only content.
- Make the existing Connect action explicitly retry the configured server even when the URL is unchanged during fallback. Pass that intent to the transport rather than relying only on URL comparison. Closing unchanged settings or changing UI-only preferences must not retry or leave fallback.
- Reconnect is an intentional destination change: invalidate local callbacks, close readiness gates, retain drafts, drain admitted local writes, and run the existing startup reconciliation strategy (`ask`, `server`, or `local`) before enabling server actions. A recognized connection failure returns to local initialization without clearing the configured URL. A successful connection restores the server badge and normal remote-update approval behavior after the relevant resources are ready.
- Change startup/reconnect reconciliation into discovery followed by application. Read and classify both local/server note and task resources before dispatching any automatic reconciliation write. If either discovery read fails or becomes obsolete, apply neither resource; recognized connection failures initialize local fallback. HTTP or invalid-data failures remain explicit initialization errors rather than triggering fallback. No mutation readiness opens on an incomplete discovery, and a later deliberate Connect retries it.
- After successful discovery, honor the existing per-resource strategy, including empty server content and empty-local adoption. Recheck the generation before every write. Track each resource as unchanged, awaiting choice, applied, failed, or outcome unknown, with its last attempted direction. For a later failure, retain completed outcomes, stop further automatic application, and show which resources changed or remain uncertain. Do not roll back or replay completed/uncertain writes. A failed mutation alone does not trigger fallback; a later qualifying GET failure may do so. Reread actual local files after the ordering barrier before enabling fallback, and reclassify uncertain server state on a deliberate retry rather than assuming the failed write did not land.
- Do not promise unchanged local files after reconciliation application begins. Explicit Connect authorizes the configured overwrite strategy; a successful note application can survive a later task write failure. Explain partial outcomes in the connection status and keep pending resource choices explicit. Discovery failure, unlike application failure, performs no reconciliation writes. Existing server backups already admitted before Connect may still finish under the ordering barrier and are not reconciliation rollback candidates.
- Keep fallback active until explicit Connect or app restart. Do not automatically switch an editing session back to the server just because an SSE connection recovers. The existing Use local files action still clears the configured URL and selects deliberate local mode.

- For the readiness barrier, defer local loading and reconnect discovery/application in separate tests. ## Acceptance Criteria

- With a saved but unreachable server URL, the app displays existing local tasks, note, and remembered labels after connection failure, not only the reported label error.
- Both panes, connection badges, local watcher events, and subsequent writes consistently use the same local destination. Empty local files display normal empty states; genuine local read errors remain visible.
- The server URL and TLS preference remain saved. Certificate validation is never weakened automatically. A clear status identifies local fallback.
- Concurrent or obsolete failures cannot repeatedly transition the app or override a newer destination. Late server responses cannot overwrite local content or clear newer drafts.
- Both transition directions close mutation readiness synchronously; no user mutation can bypass initialization by capturing a fresh context. Mounted drafts survive, old projections cannot authorize new-destination actions, and readiness opens only for a loaded current-generation resource with required choices settled.
- Already-admitted native local writes settle before local projection loading/editing or reconnect reconciliation; no old backup can overwrite a subsequently enabled local edit. Unsettled native writes expose a waiting state and never release the barrier through a timeout alone.
- Failed mutations are never replayed against local storage. Server task IDs cannot be used for local mutations, and dirty drafts require the existing explicit cross-destination choice before persistence.
- Connect retries the saved URL during fallback, including an unchanged URL. Success uses existing reconciliation choices and restores server behavior. Discovery failure applies neither resource and a recognized connection failure returns to local loading after the storage barrier. Unchanged settings do not reconnect.
- Failures after reconciliation writes begin preserve and report per-resource applied/failed/unknown outcomes; no transactional unchanged-files guarantee is made. Fallback rereads the actual settled local files, and retry reclassifies uncertain server state without replaying old actions.
- HTTP response errors, invalid response data, and an SSE-only outage retain existing error/retry behavior rather than silently switching stores.
- Existing approval, note-save ownership, project-operation, local-mode, and connection-recovery regressions pass alongside new fallback tests.

## Risks And Decisions

- Local files are the existing data-directory contents, not a guaranteed fresh or per-server cache. Display them as local files; do not claim they mirror the latest server state or introduce a new backup format.
- Fallback is a whole-app destination change, not a read-through cache. Mixing server tasks with local writes could mutate unrelated task IDs and is explicitly prohibited.
- Preserve normal local editing rather than introducing a new read-only mode. No automatic upload queue or background merge is added. Explicit reconnect may overwrite a side according to the user's existing reconciliation strategy; document this behavior.
- Initialization is temporarily mutation-blocked, not a new permanent read-only mode. Effective destination and mutation readiness are distinct; `ready` for mounting must not be used to discard an existing pane's draft or pending-save owner.
- JavaScript generation checks cannot recall native file writes already dispatched. Drain registered local operations before establishing the next writable projection. A stuck native local write trades availability for data safety; expose it rather than falsely declaring local storage safe. Do not extend this wait to unrelated pending server requests.
- Two-resource discovery prevents partial adoption on a discovery GET failure, but application is still per-resource and nontransactional. The configured `server` strategy can intentionally replace a nonempty local note with an empty server note. Partial successes and uncertain mutations must remain visible; no cross-resource rollback or offline merge subsystem is added.
- Explicit reconnect avoids unrequested destination changes while editing and keeps recovery scope small. Resource HTTP errors and SSE reconnect behavior otherwise stay unchanged.
- Startup reconciliation currently swallows errors, and settings comparison currently uses URL identity. Both paths must participate in the new state lifecycle; fixing only `getLabels` would leave note loading, writes, and recovery inconsistent.
- Native mutations already accepted by the server cannot be recalled. Preserve single-flight save ownership and do not treat a network error as proof that a mutation failed before reaching storage.
- Respect unrelated working-tree changes, including `todo.md`. This planning commit contains only this task's `2-plan.md`; implementation work will require a separate `app/` submodule commit and parent pointer update.
