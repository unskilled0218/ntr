## scope

Update only the `server/` submodule's container image and release tooling, following `https://git.lan/dev/container-release-template` at commit `3c73528231ac1cbdd43600a5ca723390db804bac` (template version `0.5.0`). Adapt its supported Bash entry point, standard-library Python helper, strict JSON settings, committed version/notes, digest-bound publication, and package association to `ntr/ntr-server`. Preserve the Rust application's endpoints, storage semantics, non-root execution, environment settings, and persistent paths. No app changes, live publication, source push, privileged host preparation, retention, package reassignment, or edits to `todo.md` are authorized by this task.

## Implementation Plan

### 1. Pin the reference and map migration behavior

- Retrieve reference files by the exact commit above, not a moving branch: `scripts/release.sh`, `scripts/release-common.sh`, `scripts/release-data.py`, `scripts/release.json`, `tests/test_bash_release.py`, and its required fixtures. Inspect helper imports, fixture dependencies, and documentation before porting. Record the source pin and intentional server-specific deviations in the server's release documentation; do not add unknown provenance fields to the template's strict settings schema.
- Map existing `server/scripts/image_release.py` and `server/tests/release_script_test.py` behavior to the new contract before retiring them. Preserve applicable protections and coverage for TLS, secret isolation, destination validation, immutable digest/config checks, engine/context selection, conflicts, accepted-but-lost responses, and preservation of accepted remote state. Replace obsolete archive/version-image expectations deliberately rather than weakening unrelated safety assertions.
- Treat this as a supported-workflow migration, not an updater installation. Preserve existing remote Git tags, releases, packages, images, generated local `server/release/` archives, and historical task records. Old transactions remain tied to their original checkout/scripts; the new workflow must refuse foreign or ambiguous evidence rather than adopt it as its own.

### 2. Adopt configuration, credentials, and version conventions

- Replace the Python-launcher-only entry point with the reference's Bash orchestration and standalone helper. Add `server/scripts/release-common.sh`, `release-data.py`, and strict schema-1 `release.json`. Set `gitea` to `https://git.lan`, `repository` to `ntr/ntr-server`, `image` to `git.lan/ntr/ntr-server`, platforms to exactly `linux/amd64` and `linux/arm64`, and the notes path to the prepared server release notes. Keep all copied Hello World/template repository targets out of active settings and tests' default consumer configuration.
- Configure `username` as `dev`, matching the current server checkout's effective Git username, while documenting that it must match the token owner, not necessarily the `ntr` package owner. Preserve `GIT_USERNAME` as the reference's optional login override. This local configuration is not proof of account permissions; do not read a real token to validate it.
- Adopt the protected external token file convention, default `~/.config/git/token`, with `GIT_TOKEN` overriding the file path, never supplying inline token content. Enforce ownership, regular-file/non-symlink status, restrictive permissions, and exclusion from the project. Do not create or copy real credentials. Reject deprecated `FORGEJO_*` release overrides with a migration error before credentials or external effects, rather than silently ignoring an old target/token override and publishing with unrelated defaults.
- Add `server/VERSION` as the canonical release version and prepare the next server patch, currently `0.2.5`, not the template's `0.5.0`. Keep `Cargo.toml` and the `my-ntr-server` entry in `Cargo.lock` as required Rust metadata mirrors of `VERSION`. Extend local settings validation using Python 3.11's `tomllib` to reject mirror mismatches without invoking Cargo or modifying files. Add committed `docs/releases/0.2.5.md`, beginning `# Release v0.2.5`, with project changes only; settings, notes path/header, README's prepared version, and Rust mirrors must agree. Never overwrite an existing conflicting version/tag.
- Support only no-argument publication, `--validate`, and `--help`. Help requires only Bash. Validation checks settings, version mirrors, notes, and active paths without reading credentials, creating locks/temp state, invoking Docker/Git publication, or contacting services. Reject extra/unsupported arguments before credentials or effects. Add the template's state/lock paths to `.gitignore` while retaining existing data/archive/cache ignores.

### 3. Port the supported publication workflow

- Port the reference's bounded I/O, strict parsing, source/config/script identity, private committed-source snapshot, local filesystem lock, complete remote inventories, source-remote verification, exact deterministic annotated tag, and read-before-write guards. Require a clean, already-pushed server `main` and exact configured fetch/push destinations; do not push source automatically or inspect the unrelated parent/app working tree as a release prerequisite.
- Use the operator's selected, already-prepared Buildx builder and verify both platforms before publication. Stop if prerequisites are missing. Do not automatically create/select `ntr-release`, install emulation, change Docker contexts, or rewrite client/daemon/BuildKit trust. Preserve the caller's host/context/TLS and Buildx state selection when isolating registry authentication.
- For a fresh version, capture the predecessor `latest`, reuse only matching verified staging or build once from the committed snapshot, verify the immutable multi-platform index/config labels, publish the exact non-force annotated Git tag, promote the verified digest to `latest` without rebuilding, create the notes-only release, and verify all final identities before package association and success. Use the reference's `container-release-bash/1` identity format and its source/config/scripts/notes binding rather than trusting a tag name alone.
- Replace the old versioned image tag and `img.tar.gz`/checksum attachment contract with the reference's staging/digest plus mutable `latest` contract. Do not add archive creation, extra public version-image aliases, arbitrary hooks, retention, or remote cleanup as compatibility layers. Existing older version tags/images and archive attachments remain usable historical artifacts and must not be deleted or rewritten.
- Preserve reference retry distinctions: absent tag/release may reuse verified staging; a fully matching completed publication is verified without build/promotion/tag/release writes; tag-only, release-only, foreign, incomplete, or changed identity states refuse automatic repair. A running invocation may reconcile its own lost response through fresh exact evidence, not repeated blind mutation. Partial failures return nonzero and retain accepted state; no rollback, force push, or automatic tag/release creation by the release API is allowed.

### 4. Close the reference's two known publication warnings

- Address the reference's documented N1 within this port: after digest promotion is confirmed, make that a one-way state transition. Subsequent guards must require `latest` to remain the prepared digest, not also accept its captured predecessor. Before release POST and package association, a failed read, predecessor reappearance, missing alias, or foreign digest must stop without repromotion, release creation, rollback, or cleanup. Keep the pre-promotion predecessor allowance separate from post-promotion authority.
- Address N2 without regressing the existing server publisher's plugin compatibility: private Docker auth must preserve discovery of the selected Buildx executable, including one installed only under the original Docker config's `cli-plugins`. Preserve approved executable discovery paths separately from auth/helper settings, and verify consistent plugin availability under the isolated configuration before publication writes. Never copy the original registry credentials or credential-helper inventory into the private config. If stable selection cannot be established, refuse before mutation rather than silently using another installed plugin.
- Add full-entry regressions that inject alias reversion after confirmed promotion and config-local plugin discovery under isolated auth. Assert the intended fault was actually reached and no prohibited later write occurred. Record these as local deviations from the pinned template, not claims that upstream has fixed its warnings. Do not claim publication readiness while either ported warning remains unresolved; record a blocker if it cannot be closed safely.

### 5. Integrate the real Rust image and Compose deployment

- Keep `server/Dockerfile` as the real multi-stage Rust build, never the template's Ubuntu Hello World image. Preserve `cargo build --release --locked --bin my-ntr-server`, compatible Rust/Bookworm build/runtime images, runtime CA certificates/curl/libgcc, UID/GID `1000:1000`, `/data` ownership, port `8080`, all existing resource-path environment defaults, and the binary entry point. No application dependency or runtime-distribution migration is needed for adopting the release template.
- Adapt release image metadata to the template's verified Buildx `--label` values for version, source, and full revision. Remove or reconcile old build-argument-only label wiring so a new release cannot accidentally contain empty/conflicting labels. Retain the narrow `.dockerignore` allowlist so credentials, runtime data, scripts, caches, archives, and untracked files do not enter image layers. Include extra version/build inputs only if the Dockerfile actually consumes them.
- Change the Compose image reference to `git.lan/ntr/ntr-server:latest`, which the new workflow actually publishes, instead of inventing a nonexistent new `:0.2.5` image tag. Keep the explicit non-root user, loopback host mapping, persistent bind mount, health check, and restart policy unchanged. Document immutable deployment with the verified index digest as the preferred reproducible alternative; `latest` is mutable and may not exist until a separately approved first publication. Do not pull or deploy it during this task.

### 6. Verify package association without expanding authority

- Port exact repository/package identity checks and the package-wide association step only after publication is proven. A correct existing link is read-only; an observed conflicting link is a refusal, never an unlink/reassignment. Require an explicit nullable `repository` field, exact owner/name/type/version, positive IDs, and refreshed evidence. Use the literal package version `latest`, not the `/-/latest` selector, and derive the package name from the image setting.
- Preserve the pinned reference's stable-Gitea-`1.25.x` new-link gate and its hidden-link protection. Other families, development builds, failed version reads, malformed identity, or unknown evidence must not authorize a POST. A correct existing association may verify without that write gate. Do not infer deployed API compatibility from the site branding/footer or weaken the version gate to accommodate it. Additional server families require separate contract analysis and approval, not a guessed compatibility switch.
- Preserve one bodyless scoped link POST, required empty 201 response, read-back verification, and exact lost-transport-response reconciliation without repeating the write. Keep final publication and link checks before success. Unsupported or uncertain linking returns nonzero and preserves any already accepted publication; no deletion or rollback follows. Document that exclusive package writers are an operator prerequisite, the local lock is not distributed exclusion, and the package link affects all versions. No live API link or publication is performed as verification.

## Acceptance Criteria

- The server has the reference-derived Bash/Python-standard-library workflow and strict project-specific settings, with no active template sample targets or old-engine dependency. Prepared server version, committed notes, Rust metadata mirrors, README, and settings agree; validation enforces that agreement without effects.
- `--help` and `--validate` are usable without a token, Docker daemon, registry, or remote Git access. Publication requires the configured clean/pushed server `main`, both platforms, private external token-file credentials, and complete bounded evidence. Deprecated target/token overrides cannot be silently ignored.
- Publication builds/reuses verified staging from committed source, verifies both image platforms and OCI labels, binds immutable identity in an exact annotated non-force Git tag, promotes by digest to `latest`, creates the notes-only release, and verifies the allowed package association before success. Conflicts, partial states, unsupported association writes, and failed evidence refuse safely without rollback, cleanup, or blind replay.
- The port does not retain N1's post-promotion predecessor allowance or N2's config-local Buildx discovery regression. Fault-injection tests demonstrate the actual unsafe transition is blocked, with no prohibited subsequent writes. Private auth does not change the selected engine/context/plugin or import unrelated credentials.
- The Rust image still runs `my-ntr-server` as UID/GID `1000:1000` with the existing data paths, port, environment contract, and Compose health/storage behavior. Compose references a published-contract alias (`latest`) or a documented verified index digest, not a newly assumed version-image alias. Architecture/runtime checks are passed or explicitly recorded as unavailable.
- Applicable old release-safety behaviors remain covered under the new contract, Python/shell/Rust checks pass or have exact documented blockers, and active documentation/tests agree on the migration. No live publication, package mutation, privileged preparation, app changes, dependency upgrade, unrelated cleanup, or edits to `todo.md` occur during implementation verification.

## Risks And Decisions

- The reference changes operator-visible behavior, not just filenames: versioned container aliases and archive attachments are replaced by digest-bound Git tags, staging, and mutable `latest`. The Compose/docs migration must be explicit; historical artifacts remain untouched. Do not extend the template with an unrequested compatibility publisher.
- Rust still requires a Cargo version even though the reference has no module-version metadata. `VERSION` is authoritative for releases; Cargo package/lock values are checked mirrors, not independent sources or automatically rewritten publication inputs.
- Template `0.5.0` contains two documented unresolved warnings. Copying it verbatim would knowingly import an unsafe post-promotion write path and regress the server's existing plugin discovery support. Their narrowly scoped port fixes and regressions are part of adoption, not work on the upstream repository.
- New package links are supported only where the reference's reviewed server contract permits them. The deployed server family and real account permissions are not established by local files or fake-port tests. An unsupported/null link can leave a verified publication incomplete; document this before any later live approval rather than skipping association or weakening guards.
- Publication crosses Git, registry, and repository/package APIs without a distributed transaction. Exclusive writers, safe refusal, immutable identity, and accurate partial-state reporting reduce risk but cannot make those services atomic. Never add repair-by-deletion, force pushes, alias rollback, or package reassignment.
- Retiring the old publisher can silently lose safety if tests are merely replaced by upstream fixtures. Keep an explicit behavior mapping and ensure each fault test reaches its intended boundary with valid server metadata. Passing local suites is not authorization or evidence for live writes, real plugin routing, TLS, or emulated runtime execution.
